## 设计目标和边界

AI 监督是一个显式启动的、多终端调度与审查机制，不会自动启动。它只管理配置时选中的工作终端（`surfaceId`），并以此 ID 而不是终端显示名称识别通道，避免同名终端串线。

它把职责分开：调度器负责在合适时机发送任务并管理状态；**每个 lane 都有一个独立、可见的专属“AI 监督”终端**，只读取并裁决其绑定的一个工作终端；人类负责最终确认停止条件，或处理权限、信息不足等阻塞。工作终端不会收到监督协议正文，只有应执行的任务文本。

```text
侧栏配置 ──启动──> 调度器（Renderer/App） ──写入──> 工作终端 A ──Hook──> 监督 AI A
     │                       │                              │                 │
     │                       ├──────────────写入──> 工作终端 B ──Hook──> 监督 AI B
     │                       │                                                │
     └──人工确认 <────────────────通知/记录面板 <─────审计记录 + wmux supervisor decide
```

## 两种运行模式

| 模式 | 工作终端收到的内容 | 适用场景 | 自动推进边界 |
| --- | --- | --- | --- |
| 直接注入（`direct`） | 配置的每一行指令，**原样**发送，不附带目标或停止条件。 | 人类已拆好步骤，希望逐条执行。 | 全部指令完成后只触发停止条件核对，不会自动收工。 |
| 目标追逐（`goal-chase`） | 目标、允许范围、禁止项、完成条件与“最小下一步”提示。 | 目标清楚但下一步需由 AI 决策。 | 每个通道最多自动决策 `maxAutoSteps` 次（默认 8）；用尽后通知人工。 |

两种模式都要求填写停止/完成条件，并支持两类判据：

- **方向型**：期望的终态，例如“用户能登录且错误提示正确”。监督 AI 综合进展判断是否形成可交付闭环。
- **具体条件型**：可验证的事实，例如“`npm test` 全绿”或出现 `BUILD SUCCESS`。监督 AI 应引用终端证据判断。

“指令队列为空”与“任务完成”严格不是一回事。停止条件只有在侧栏人工确认，或监督 AI 通过 CLI 提交 `complete` 裁决后才会使该通道停止。

## 运行时状态与调度规则

每个被监控终端对应一个 lane，包含步骤队列、自动决策计数及以下关键状态：

- `supervisorSurfaceId`：该 lane 专属监督终端的 ID；监督终端与工作终端同处对应 pane，作为可见标签页。
- `pending` / `in_progress` / `completed` / `skipped`：步骤状态。
- `awaitingReview`：工作 Agent 本轮结束，必须先得到监督裁决；此时调度器不会继续发送任何任务。
- `awaitingStopCheck`：步骤完成后正在核对停止/完成条件；同样不会继续注入。
- `stopConfirmed`：停止条件已确认，lane 被禁用。
- `currentTask` 与 `decisions`：该工作终端最近任务及最多 100 条内存裁决时间线，供侧栏按 lane 展示。

调度器默认每 4 秒轮询一次（最小 1.5 秒）。仅当 Agent 状态是 `idle` 时发送任务；`unknown` 状态默认不发送，除非配置允许未知状态。`working` 或 `blocked` 状态绝不发送。任务发出后，调度器会等到终端已稳定空闲，并且观察到工作态（或等待更长时间）后，才把该步骤标为完成。

`blocked` 不等于完成：系统暂停该 lane、通知用户并避免重复提醒。目标追逐模式在自动步数达到上限时也暂停并通知用户。

## 逐轮监督与裁决协议

工作 Agent 的 Hook 将 `UserPromptSubmit`、`Stop`、`StopFailure` 与 `Notification` 事件送入 wmux。对已纳入监督的 lane：

1. 收到任务事件时，系统清除上一轮的评审等待，并把任务摘要转发给监督终端。
2. 收到 `Stop` 或 `StopFailure` 时，系统把 lane 标为 `awaitingReview`，要求监督 AI 先执行 `wmux read-screen --surface <工作终端ID> --lines 80` 查看证据。
3. 监督 AI 通过下列命令静默提交裁决：

   ```powershell
   wmux supervisor decide --surface <工作终端ID> --outcome <continue|rework|complete|needs-human> --reason "结论" [--next "下一条指令"]
   ```

4. CLI 会附带调用者自身的 `WMUX_SURFACE_ID`。命名管道的 V2 bridge 只有在该 ID 等于目标 lane 的 `supervisorSurfaceId` 时才接受裁决；成功时不向监督终端打印结果，避免污染其上下文。

裁决的当前语义如下：

| 结果 | 系统行为 |
| --- | --- |
| `continue` | 解除本轮评审等待；若提供 `--next`，立即发送这条指令。 |
| `rework` | 当前实现与 `continue` 相同，但审计日志保留不同结果，供后续区分返工策略。 |
| `complete` | 直接确认该 lane 的停止/完成条件、禁用该 lane；若所有 lane 都停止，则结束整场监督。 |
| `needs-human` | 保持评审等待，并向用户发送系统通知，等待人工处理。 |

侧栏也提供“未达到”和“已达停止条件/已达完成条件”按钮。前者解除停止核对等待，使后续工作可以继续；后者禁用当前 lane。配置页会为每个选中的工作终端在其所在 pane 创建专属监督终端，默认启动命令为 `codex`（可覆盖或留空）；创建监督终端本身不等于启动调度器。

配置页还可选择 Markdown/文本计划文件。其内容只会写入每个专属监督 AI 的 briefing，作为该任务的最高方向与约束：与表单中的目标、允许范围或禁止项冲突时，监督 AI 必须以计划文件为准（但仍不得绕过安全边界或人类明确指令）。计划文件不会注入工作终端，也不会自动执行其中的步骤；侧栏会显示已选择的文件名。

计划文件使用现有的受限文件选择器，只支持 Markdown/文本格式，且内容最多 30,000 个字符。选择时会将文件内容保存为当前监督会话的快照；磁盘文件之后发生变化不会自动刷新，需重新选择。运行中的专属监督 AI 已拥有旧计划上下文时，应使用“重头再来”创建干净会话，再按新计划重新启动。

## 推荐配置流程

1. 在侧栏打开“AI 监督”，选择一个或多个工作终端。
2. 选择直接注入或目标追逐模式，并填写停止/完成条件。
3. 如有任务计划，选择计划文件；确认其约束和方向可作为监督依据。
4. 保持默认启动命令 `codex`，或按需替换/清空。
5. 点击“创建专属监督 AI”后，每个工作终端会在所在 pane 获得一个可见的监督标签；确认后点击“启动”开始调度。
6. 在侧栏按 lane 查看当前任务、裁决记录和计划文件名；更换计划或需要清空上下文时使用“重头再来”。

## 上下文隔离、可见记录与重置

专属监督终端首次启动时只收到自己的工作终端名称、`surfaceId`、当前状态、目标/停止条件和裁决规则。其提示词明确禁止读取、总结或裁决其他终端；之后的 Hook 通知、空闲提示和停止核对也都通过该 lane 的 `supervisorSurfaceId` 定向发送。因此多个任务不会共享监督 AI 的模型上下文。

配置页的“恢复最近审计上下文”默认开启。创建替代监督 AI 时，系统从工作终端自己的项目目录读取最近可用审计，恢复任务、终端事件和监督裁决的有界摘要，并把来源会话 ID 显示在侧栏和该专属监督 AI 的 briefing 中。优先按稳定的 `surfaceId` 匹配；若终端恢复后 ID 已变化，只有同项目内该显示标签对应唯一历史终端时才回退匹配。多个同名终端一律不恢复，宁可缺失历史也不混入别人的任务上下文。

恢复前的审计仅是背景，监督 AI 必须先读取当前终端屏幕再作裁决。恢复不会还原旧的计划文件、旧调度设置或旧监督终端模型上下文；需要时用户重新选择计划文件。可以在配置页关闭恢复。

侧栏在每个 lane 下显示最近任务、专属监督是否连接，以及逐条绑定任务的裁决记录（时间、结果、原因或下一步）。提交裁决时，记录同时写入内存时间线和对应项目目录的审计流。

“重头再来”会要求确认，然后：停止并关闭全部专属监督终端、为旧 lane 写入 `session.abandoned` 审计事件、清空当前会话的任务/裁决/调度状态，并重新打开配置页。它不会删除历史 `.wmux/supervisor/<sessionId>/` 文件，因此旧记录仍可审计；但 `session.abandoned` 同时是恢复屏障，新会话不会继承该终端更早的上下文或内存决策。

## 通知与审计

监督运行期间，普通 Agent 生命周期通知会被抑制，避免与监督通知重复。用户仍会在下列情形收到监督侧通知：Agent 阻塞、指令队列完成但待核对、目标追逐需人工接管、或监督裁决为 `needs-human`。

每场监督会话会在每个工作终端的项目目录写入：

```text
<projectDir>/.wmux/supervisor/<sessionId>/
  session.json       # 会话元数据
  events.ndjson      # 一行一条事件：启动、任务、生命周期、监督裁决等
```

事件包含版本、时间、事件类型、终端元数据和裁决载荷；字符串字段会截断，避免审计文件无限膨胀。恢复最多检查最近 50 个会话；读取单个审计文件时限制为 2 MiB、最多取最近 200 条事件，读取或解析失败时会跳过，不影响监督启动。实现会在项目 `.gitignore` 中补充 `.wmux/supervisor/`，使审计目录默认不纳入版本控制。

## 当前实现注意点

- 监督 AI 的“达到”文本本身不是状态变更；必须由人工点击侧栏确认，或由 AI 调用 `wmux supervisor decide --outcome complete` 落实。
- `continue` 和 `rework` 目前的调度效果相同，区别只体现在审计结果；若要引入自动返工策略，需要补充二者的状态机差异。
- 侧栏保留了“待批准”数据结构与 UI，但当前调度主路径直接发送任务，未见生产路径把决策加入待批准队列；它尚未构成目标追逐的强制人工审批门。
- 审计目录写入的是被监控终端启动时记录的 `projectDir`；无工作目录的 lane 不会落盘。
